# 网络通道：蓝牙与 Wi-Fi 局域网

通知桥只有两条连接路径：低功耗蓝牙和同一 Wi-Fi 下的局域网直连。没有远程中继，也没有需要手动填写的服务器地址。

## 两条路径

| 路径 | 适用场景 | 需要什么 | 加密 |
| --- | --- | --- | --- |
| 蓝牙 | 手机在 Mac 旁边（约 10 米内） | 蓝牙 | BLE 链路，应用层明文 |
| Wi-Fi 局域网 | 手机和 Mac 在同一个 Wi-Fi | 同一个局域网；Bonjour/mDNS | 局域网内明文（与蓝牙一致） |

局域网通道使用手机上的 TCP 服务（端口 `47821`），Mac 通过 Bonjour 自动发现，不需要任何配置。

## 自动切换

Mac 端会同时运行蓝牙和局域网接收器，不会因为一条通道可用就关闭另一条：

- 任何一条通道到达的通知都会进入同一个通知中心入口。
- 通知用「手机端稳定 ID + 手机发送时间」去重，所以同一条消息从蓝牙和局域网同时到达时只弹一次。
- 真正的新消息（同一会话的新 post time）不会被去重掉。
- 菜单栏「状态」显示当前可用的路径，例如「已连接：蓝牙 + 局域网」。
- 局域网断开后按 2/5/15/30/60/120 秒退避重连；手动「重新连接网络通道」会立即重试。

手机端不需要切换：BLE GATT server 和 TCP 服务同时运行，每条通知会分别尝试两条通道。

## 局域网 TCP 协议

手机是服务端，Mac 是客户端，和 BLE 的角色一致。

```text
4 字节大端长度 N
N 字节 UTF-8 JSON
```

最大帧 256 KiB。消息类型：

| 方向 | 类型 | 说明 |
| --- | --- | --- |
| 手机 → Mac | `hello` | 连接后立即发送设备 ID、名称、服务端 session |
| Mac → 手机 | `auth` | 6 位配对码，可带上次的 session 和 last seq |
| 手机 → Mac | `auth_ok` | 配对成功，返回通知访问状态、当前 head、session |
| 手机 → Mac | `auth_fail` | 配对码错误；同一连接连续 5 次后断开 |
| 手机 → Mac | `notification` | `seq` + 原始通知 JSON（`data`） |
| Mac → 手机 | `ack` | 已处理到该序号 |
| 双向 | `ping` / `pong` | 心跳；手机 45 秒无数据会关闭连接 |

### 断线补发

手机保留最近 500 条通知的环形历史。Mac 在 `auth` 里带上次的 session 和 last seq；如果 session 相同，手机会把 seq 更大的通知补发过来。Mac 每收到一条就 ACK，并持久化 last seq。

- 手机服务重启后 session 变化，Mac 会从当前 head 重新开始，不会把旧历史全部重放。
- Mac 首次配对不发送 `since`，避免第一次连接就收到 500 条旧通知。
- 局域网断开、Mac 睡眠、Wi-Fi 切换后，重连即可补上这段时间的通知。

### 发现

手机通过 Android `NsdManager` 广播 `_notifybridge._tcp`，TXT 包含 `id`（8 字节设备 ID 的十六进制）和 `name`。Mac 用 `NWBrowser` 浏览，按已配对设备 ID 过滤；没有发现时只等待下一次广播，不再提供手动地址。

## 安全边界

- 蓝牙和局域网都是应用层明文；它们只适合你信任的近距离网络。局域网流量不会离开本网段。
- 配对码保存在设备本地偏好设置里，没有 Keychain/Keystore 生物识别保护。能登录本机账号的进程理论上可以读取。
- 这是一个自用原型，不是企业级消息网关。

## 已知限制

- 手机必须开机、有电；短信/微信仍然先到手机。手机不在线时，Mac 收不到这段时间的通知。
- 局域网需要手机和 Mac 处于同一个 Wi-Fi，且路由器没有开启客户端隔离（AP isolation）。访客网络、企业 Wi-Fi 或部分路由器的隔离设置会让 mDNS 发现失败。
- 网络通道复用了原来的前台服务，Android 启动流程仍要求蓝牙权限和蓝牙开关；不需要蓝牙连接，但需要保留这些权限/开关。
- Android 厂商的后台限制可能杀掉前台服务；需要电池优化白名单。部分 ROM 还会限制 Wi-Fi 休眠或 mDNS。
- 当前没有实现通知点击跳回手机、快捷回复、通知撤销同步。
